## The change: a merged article is a redirect, and a redirect is not a sitemap URL

Measuring the blog delta meant fetching all 137 URLs in `blog.xml` with `redirect: manual`.
**136 answered 200 at the listed URL. One answered 308:**

```
308  /blog/quand-prendre-de-la-creatine-le-guide-complet-pour-optimiser-vos-resultats
  →  /blog/comment-utiliser-la-creatine-en-tunisie-pour-maximiser-vos-performances
```

`sitemapSources.ts`'s own header already states the rule it was missing: *"legacy URL shapes;
middleware 301s them to the canonical form. Submitting a redirect is the 'Page with redirect' bucket
in Search Console."* The 29/09 fold recorded its 86 mappings in `blogMerges2909.json`, and
**`middleware.ts` redirects every key of that map unconditionally** — before the article is ever
resolved, and for the Arabic slugs too (`redirects.js` carries only the ASCII subset). So a key of
that map can never serve a 200 at its own URL. `blogArticlesSource` simply never read the map.

**Why exactly one of the 86 leaked** — and this is the part worth remembering: the other 85 were
unpublished along with the fold, while this slug is the one `sitemapData.ts` already documents as
claimed by **two** published rows (article ids 44 and 45, measured 2026-08-10, "which is why 224
published articles yield 223 URLs"). One row of it survives in `/all_articles`, so the crawl still
hands it over.

The guard reads the **same map** the middleware reads and normalises it the **same way**
(`trim().normalize('NFC').toLowerCase()`, plus the whitespace collapse `encodeBlogSlug` performs,
because a handful of CMS slugs were saved as their raw Arabic title and carry literal newlines —
measured today: 0 of the 86 keys and 0 of the 137 listed slugs are affected, so that half changes
nothing now and keeps the two sides comparable if the next fold touches one). The count is printed
in the source's note, beside the collision count the file already prints: a published row the repo
redirects away is a disagreement worth seeing, not a silent subtraction.

**Proved able to fail** against the REAL `blogArticlesSource` with only the network stubbed (the
`@/util/sitemapCrawl` and `@/services/api` modules), fed the 137 slugs production listed this
morning, old code reproduced by handing the same code path an empty map:

| | URLs submitted | redirecting URLs still listed |
| --- | --- | --- |
| old code | 137 | **1** |
| new code | **136** | **0** |

Exactly one URL dropped, **0 added, every other entry byte-identical**. Plus 8 edge cases through
the same real source, all passing: a plain ASCII merged key → excluded; the same key upper-cased →
excluded; the same key with surrounding whitespace → excluded; an Arabic merged key → excluded; that
Arabic key with a literal newline inside → excluded; a **survivor** → kept; an unrelated live article
→ kept; a slug that merely *starts with* a merged key → kept.

**Not observable until the deploy runs.** `deploy-frontend.yml` regenerates the sitemaps, so the test
is tomorrow morning: `blog.xml` must hold **136 `<loc>`** and must not contain the slug above. The
URL itself keeps 308-ing, which is correct and is not what is being watched.
