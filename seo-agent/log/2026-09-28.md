## The P0: Next.js was streaming our metadata *to Googlebot only*, and sometimes losing it

`/sante-vitalite` has now served Googlebot a complete `200` with a fully rendered body and **no
`<title>`, no canonical, no meta description and no `robots`** on two consecutive runs. On 25/09 I
called it a transient and refused to invent a cause. Today I found the cause, and it is neither
flaky nor confined to one page.

**Measure first.** Same URL, two user agents, byte offset of `<title>` in the response:

| URL | as Googlebot | as Bingbot |
| --- | --- | --- |
| `/proteines` | `<title>` at **268,738** of 272,966 | at 4,504, inside `<head>` |
| `/prise-de-masse` | at **288,904** of 293,075 | at 4,502, inside `<head>` |
| `/blog` | at **636,169** of 904,637 | at 3,827, inside `<head>` |
| `/sante-vitalite` | **absent** on one fetch (259,255 bytes, body rendered), at 259,338 on the next | at 4,507, inside `<head>` |

`</head>` closes at byte ~10,400 on these documents. So for Googlebot the head Google parses first
carries **none** of the four, and the tags arrive a quarter of a megabyte later, at the end of the
body, to be hoisted into the head by React. Bingbot gets them in the head on every single fetch of
the same URL, through the same route.

**Why.** Next.js 15.2+ streams metadata instead of blocking the shell on `generateMetadata`, except
for the user agents listed in `next/dist/shared/lib/router/utils/html-bots.js` — and the main
Googlebot is deliberately **not** on that list ("only the main Googlebot search crawler executes
JavaScript"). Bingbot, applebot, `facebookexternalhit`, Twitterbot and every `*-Google` crawler
are. Nothing in this repository set `htmlLimitedBots`, so we were on Next's default. 32 of the 36
reachable watchlist URLs happen to land in `<head>` today only because their metadata resolves
before the shell flushes — that is a race, not a contract, and the four above lose it every time.
When the late chunk does not arrive at all, Google gets a page with no title to build a snippet
from, no canonical to consolidate the legacy `/category/<slug>` and `/shop/<slug>` duplicates onto,
and no robots directive. On a site whose central problem is indexation, that is the worst thing to
leave to chance — and it is why two consecutive runs saw the shape at all.

**The fix — one supported config key, global, humans untouched** (`frontend/next.config.js`):

```js
htmlLimitedBots: new RegExp(`${nextHtmlLimitedBots}|Googlebot`, 'i'),
```

`nextHtmlLimitedBots` is read from Next's own list at config load (guarded `require`, with a frozen
copy as the fallback for the day that internal path moves), so the default is **extended, never
replaced** — dropping a bot from that list would silently move it onto streamed metadata. Plain
`Googlebot` rather than Next's `Googlebot(?!-)` so Googlebot-Image, -News and -Video, which are on
neither of Next's two lists, are covered too.

**Verified here, with Next's own code, before shipping:**

| check | result |
| --- | --- |
| `loadConfig('phase-production-build')` (the real build path) | OK, no schema warning |
| RegExp → string conversion for `output: 'standalone'` | `…|Yeti|googleweblight|Googlebot` |
| JSON round-trip (`required-server-files.json`) | survives |
| `shouldServeStreamingMetadata(Googlebot, cfg)` — what the server asks per request | **false → blocking, in `<head>`** (was `true`) |
| Googlebot smartphone, Googlebot-Image | blocking |
| Bingbot, Mediapartners-Google, facebookexternalhit, Twitterbot, applebot | blocking — **unchanged** |
| Chrome 140, iPhone Safari, GPTBot | streamed — **unchanged** |

The cost is that a Googlebot request waits for `generateMetadata` before the shell flushes, which
is what every request did before Next 15.2. Human traffic is not affected: the flag is read per
request from the UA.

**Not verifiable live today, and not claimed:** this is a frontend change, observable only after
the merge and `deploy-frontend.yml`. The evidence above is Next's own loader and decision function
executed against the real config. Tomorrow's first action re-measures the four URLs.
