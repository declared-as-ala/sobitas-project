## The defect: "ONE link per destination" counted the body, not the page

`frontend/src/util/internalLinks.ts` states the rule its header calls first among the limits that
keep automatic interlinking from being spam:

> ONE link per destination — the second link to /proteines in the same article adds no signal and
> dilutes the anchor text of the first

`injectInternalLinks` seeds itself from the HTML it is handed, which is `articles.description` and
nothing else. The article page ships two more link blocks:

- the **"Lire aussi"** chips — `BlogSeoBlock`, from `blogSeoConfig.internalLinks`, hand-written;
- the **"Voir aussi sur la boutique"** nav — `ArticleDetailClient`, from `article.related_shop_categories`.

The route already applies the right rule for the one block it knew about: `page.tsx` drops
`commerceBridge.href` from the target list because "the bridge is already the first, strongest link
to its commercial owner". This is that same policy applied to the two blocks it was missing.

**Where the 30 land, and why it is the costly kind of waste:**

| destination | wasted links |
| --- | --- |
| **/whey-proteine** | **13** |
| **/proteines** | **9** |
| /whey-isolate · /vitamines · /mass-gainers · /creatine | 2 each |

**22 of 30 are `/whey-proteine` and `/proteines`** — the two pages behind the two largest rows in
`KEYWORDS.md` (`proteine tunisie` 683 impr at 18.5, `whey protein tunisie` 346 at 15.7, both 22/09
GSC) and the exact pages `internalLinks.ts` was written to feed. **14 of the 25 articles are at the
6-link cap**, so there the duplicate does not merely add nothing — it *displaces* a first link to a
shelf that has none.

**Which link should yield, and why it is the generated one.** The injector loses, every time:

| the shelf's two anchors on one page | |
| --- | --- |
| curated chip | "whey protéine en Tunisie" · "prix des whey chez Protein.tn" · "comparer les whey en stock" · "les whey disponibles en Tunisie" |
| injected in-prose | "whey" |

The curated anchor is the better one in every case I read, it is a human's choice, and the
precedent in this very file is that a hand-written link outranks a generated one (the bridge
exclusion). Deleting a curated chip to make room for an automatic one-word anchor would be the
wrong direction, and it would free no slot. So the injector yields, the shelf keeps its stronger
anchor, and on the 14 at-cap articles the freed slot goes to a shelf with **no link at all**.

**The fix.** `excludeLinkedDestinations(targets, hrefs)` in `internalLinks.ts` — one exported pure
function, reusing the normaliser the 30/09 fix introduced so the four ways a shelf is written still
compare equal — and `page.tsx` now subtracts all three curated sources at once (bridge + chips +
shop nav) instead of only the bridge. `blogSeoConfig.resolveBlogSeoLinks()` is new and holds the
chip-resolution rule **once**: the route and `BlogSeoBlock` both read it, because a second copy of
that rule in the second place is a copy that drifts, and the drift would be invisible (the page
still renders, it just links one shelf twice).

**Proved able to fail before being trusted** — the real modules through a resolve hook, no
reimplementation, old code vs new:

## The second fix: a false P0 that had spent two mornings

`category/[slug]/page.tsx` rethrows an upstream 429/5xx/timeout **on purpose**, and the code says
why in as many words: Next then answers with a 5xx it never caches and the crawler simply retries,
which beats caching a 200 that carries the generic title and no canonical. `audit-live.mjs` was
calling that intended behaviour a **P0 on a single render** — and P0 means "drop everything".

The checker already had the right rule for the analogous case: a 200 whose body rendered but whose
head carried none of title/canonical/description/robots gets **one confirming re-fetch**, because
"this checker's whole value is that exit 1 means *drop everything*, so a single flaky render must
not be able to spend a routine's entire morning". That reasoning was simply never extended to the
status code. So a 429/5xx now gets the same single confirming re-fetch after 1.5 s:

- re-fetch 200 → the page is measured from the good render and the anomaly is recorded **P2**,
  naming the first status. Visible, still counted, not a false alarm.
- re-fetch non-200 → **P0**, naming both statuses (`HTTP 500 (confirmed: re-fetch returned 500)`).
- **a 4xx gets no re-fetch and stays a P0 on the first look** — 404/410/403 are states the origin is
  sure about and they do not clear on a retry.

**Proved able to fail**, against a local fake origin (`BASE_URL` override), before being trusted:

| probe | exit | verdict |
| --- | --- | --- |
| `/flaky-500` (500 once, then 200) | **0** | `P2: transient: HTTP 500 on 1 of 2 fetches` and the page measured from the clean render |
| `/always-500` | **1** | `P0: HTTP 500 (confirmed: re-fetch returned 500)` — a real outage still stops the morning |
| `/gone-404` | **1** | `P0: HTTP 404` — no re-fetch, unchanged |
| `/healthy` | **0** | `ok` |

Then on production: the 120-URL sweep exits **0** with `/sante-vitalite` recorded P2. A genuine
outage is still exit 1; three mornings of the same false alarm are over.
