## The tool (Friday slot): `seo-agent/tools/title-case-check.mjs`

BACKLOG P2, "lock today's casing contract with a check script". Yesterday's builder fix was
validated by a one-off before/after diff; nothing in the repo held it, so the next edit to
`caseToken`, `KEEP_UPPER` or `normalizeUnits` could have undone it silently and the only place it
would have shown is the SERP, weeks later.

It imports the **actual builder** — no reimplementation — through a `module.registerHooks` resolve
hook that lets Node load `frontend/src/util/*.ts` directly, then runs it over real catalogue names
from `productsBySubCategoryId/<slug>` with the brand each page passes. Five rules:

| rule | what it locks |
| --- | --- |
| a | a pinned initialism shouted in the catalogue must not come out Titlecased (`GSN` ≠ `Gsn`) |
| b | the micro sign survives and never becomes Greek capital `Μ` |
| c | no glued unit the builder normalises (`200g`, `2.3KG`, `60CAPS`) |
| d | a name the catalogue already cased on purpose keeps its capitals |
| e | 11 frozen golden pairs, offline, so a change that simply DISABLES the humanizer cannot pass a–d |

Two design decisions worth stating, both learned from `parity-check.mjs`:

- **The expectations are a frozen COPY of `KEEP_UPPER`, not an import of it.** A check that reads
  its expectations out of the thing it checks cannot catch a deletion.
- **Findings and candidates are separate columns.** A brand the shop spells `OstroVit` that a
  shouting name flattens to `Ostrovit`, or a unit the builder never promised (`2L`), is printed as
  context and never budgeted. A gate that is always red is a gate nobody reads.

It is deliberately **not** wired into `prebuild`: a live-API dependency in the build would break a
deploy the day the API is slow.

### Its first full-catalogue run found a live defect

Run over **11,367 names — the entire catalogue** (51 sub-category listings; 636 listing slugs
probed, 585 of them parent categories that `productsBySubCategoryId` correctly 404s):

    | b | micro sign survives, never Greek Μ | 2 FAIL |
      /vitamines/naturelo-vitamin-d3-625-g
        catalogue  NATURELO Vitamin D3 – 62,5 µg
        builder    Naturelo Vitamin D3 – 62,5 Μg

The micro sign U+00B5 uppercases to GREEK CAPITAL MU U+039C, so `caseToken`'s Titlecase branch
turned a standalone `µg` into `Μg`. Yesterday's pass fixed the **glued** form (`100µG` goes down
the digit branch) and its 42-listing sample never contained the **spaced** one. Fixed in
`frontend/src/util/productMetaDescription.ts` with one guard: a token that starts with the micro
sign is a unit and is never capitalised.

**Honest scope:** both affected products carry a CMS `seo_title` that wins over the humanizer, so
`Μg` is **not** in any live `<title>` today — I fetched both pages to check, and their H1s use the
raw catalogue name with the correct `µ`. This repairs the builder, not a live SERP snippet. No CTR
claim is made for it.

## The P0 that was not one — and the checker change it earned

`--sample=120` reported `/sante-vitalite` as three simultaneous P0s: no `<title>`, no canonical,
no meta description, no robots — while the same render produced 1,012 words of body and the full
JSON-LD graph. Before touching anything I measured it:

- the `--sample=40` run **45 minutes earlier** audited the same URL `ok` (title 57, description 148);
- **14 consecutive Googlebot fetches** immediately afterwards: 14/14 carried title, canonical,
  robots and description, bodies 285.7 KB each;
- nothing in the repository had changed.

One render lost its entire head. That is a transient, not a builder defect, and I am not going to
invent a cause for it. What it did expose is a real weakness in the checker: `exit 1` means "drop
everything and fix this", so a single flaky render can spend a whole morning. `audit-live.mjs` now
**confirms before it believes**: a 200 whose body rendered but whose head carries *none* of
title/canonical/description/robots gets one re-fetch; if that comes back clean the page is
measured from it and the anomaly is recorded **P2** — visible, still counted, no longer exit 1.
Missing *one* of the four is still a P0 on the first look, and if the second render is also
headless it is a P0 exactly as before.

Verified both branches against a local server that serves a headless body once and then a good
one: flaky → `P2: transient: head metadata absent on 1 of 2 renders`, exit 0; always headless →
`P0: no canonical; P0: no <title>; P0: no meta description`. `/sante-vitalite` is on the watchlist
with a note: **if this recurs on two consecutive runs it is a streaming-metadata P0**, not a flake.
